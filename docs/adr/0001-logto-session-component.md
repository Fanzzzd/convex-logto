# Session mode is a Convex component with rotating session tokens, not a BFF, cookies, or self-issued JWTs

Session mode exists to get long-lived credentials out of browser storage for apps deployed on static CDNs. Those apps have no same-site server, so no HttpOnly cookie is reachable; Convex HTTP actions live on `convex.site`, a third-party origin Safari blocks cookies for. So session mode runs the OIDC flow inside a Convex component. The component holds the Logto refresh token (Traditional Web confidential client) in its own tables, which app code cannot read, and the browser holds only a short-lived Logto ID token plus a rotating application session token. Late reuse abandons only that component Session and makes its server-held refresh token unreachable; it does not issue RFC 7009 revocation that could invalidate sibling Sessions sharing the same Logto grant. Convex keeps validating Logto's ID token itself. Self-issued JWTs and a JWKS would forfeit the zero-JWT-config value and duplicate `@convex-dev/auth`, and a full BFF is impossible without proxying away Convex's WebSocket model. Rejected alternatives: same-site cookies as the baseline (requires a custom domain or framework server most target users don't have; kept as an optional transport on top of the same component), better-auth-style cross-domain localStorage envelopes (no XSS benefit), and DPoP (not supported by Logto). Full research trail: `docs/research/`, 2026-08.
